# Требования к фронтенду системы переноса офферов Allegro

## Введение

Данный документ описывает требования к созданию полнофункционального веб-интерфейса для системы переноса офферов между аккаунтами Allegro. Система должна предоставить пользователям удобный интерфейс для управления процессом переноса офферов с поддержкой реального времени, настройки ценообразования и мониторинга прогресса.

## Требования

### Требование 1: Интеграция с существующей системой авторизации

**Пользовательская история:** Как пользователь основной системы, я хочу использовать функциональность переноса офферов без повторной авторизации, используя уже существующую сессию.

#### Критерии приемки

1. КОГДА пользователь заходит на страницы системы переноса офферов БЕЗ валидного токена в cookie, ТО система ДОЛЖНА перенаправить его на существующую страницу `/login`
2. КОГДА пользователь уже авторизован в основной системе, ТО система переноса офферов ДОЛЖНА использовать существующий токен из cookie `access_token`
3. КОГДА система создает JWT токен для API запросов к микросервису, ТО она ДОЛЖНА использовать функцию create_access_token с user_id равным PROJECT_NAME из конфига
4. КОГДА токен в cookie истекает или становится невалидным, ТО система ДОЛЖНА перенаправить пользователя на `/login` с параметром `next` для возврата
5. КОГДА пользователь использует существующую кнопку "Выйти" в основной системе, ТО он автоматически теряет доступ к системе переноса офферов

### Требование 1.1: Интеграция с микросервисом переноса офферов

**Пользовательская история:** Как система, я хочу корректно взаимодействовать с микросервисом переноса офферов, используя правильную авторизацию и базовые URL.

#### Критерии приемки

1. КОГДА система выполняет запросы к микросервису, ТО она ДОЛЖНА использовать базовый URL из конфига `MICRO_SERVICE_URL`
2. КОГДА система создает JWT токен для микросервиса, ТО она ДОЛЖНА включать в payload `user_id` равный `PROJECT_NAME` из конфига
3. КОГДА система отправляет запросы к микросервису, ТО она ДОЛЖНА включать заголовок `Authorization: Bearer <jwt_token>`
4. КОГДА микросервис возвращает ошибку 401, ТО система ДОЛЖНА обновить JWT токен и повторить запрос
5. КОГДА микросервис недоступен, ТО система ДОЛЖНА показать соответствующее уведомление пользователю

### Требование 2: Управление аккаунтами Allegro

**Пользовательская история:** Как пользователь, я хочу выбрать исходный и целевой аккаунты Allegro для переноса офферов, чтобы определить направление переноса.

#### Критерии приемки

1. КОГДА пользователь заходит на главную страницу, ТО система ДОЛЖНА загрузить и отобразить список доступных аккаунтов Allegro через API `/api/v1/tokens/user-tokens`
2. КОГДА пользователь выбирает исходный аккаунт, ТО система ДОЛЖНА отобразить его в выпадающем списке "Исходный аккаунт"
3. КОГДА пользователь выбирает целевой аккаунт, ТО система ДОЛЖНА отобразить его в выпадающем списке "Целевой аккаунт"
4. КОГДА выбраны оба аккаунта, ТО кнопка "Сравнить офферы" ДОЛЖНА стать активной
5. КОГДА пользователь нажимает "Сравнить офферы", ТО система ДОЛЖНА выполнить запрос к API `/api/v1/offer-transfer/compare-offers` и перейти к следующему шагу

### Требование 3: Выбор офферов для переноса

**Пользовательская история:** Как пользователь, я хочу просмотреть доступные для переноса офферы и выбрать нужные, чтобы контролировать какие товары будут перенесены.

#### Критерии приемки

1. КОГДА система получает список доступных офферов, ТО она ДОЛЖНА отобразить их в виде карточек с изображением, названием, ID, external ID, категорией, ценой и остатком
2. КОГДА пользователь использует поиск, ТО система ДОЛЖНА фильтровать офферы по названию или external ID в реальном времени
3. КОГДА пользователь нажимает "Выбрать все", ТО все видимые (не отфильтрованные) офферы ДОЛЖНЫ быть выбраны
4. КОГДА пользователь нажимает "Снять выбор", ТО все офферы ДОЛЖНЫ быть сняты с выбора
5. КОГДА пользователь выбирает/снимает отдельные офферы, ТО счетчик "Выбрано X из Y" ДОЛЖЕН обновляться в реальном времени
6. КОГДА выбран хотя бы один оффер, ТО кнопка "Настроить рынки" ДОЛЖНА стать активной

### Требование 4: Выбор целевых рынков

**Пользовательская история:** Как пользователь, я хочу выбрать рынки, на которые будут перенесены офферы, чтобы определить географию продаж.

#### Критерии приемки

1. КОГДА пользователь переходит к выбору рынков, ТО система ДОЛЖНА загрузить список доступных рынков через API `/api/v1/markets/`
2. КОГДА система отображает рынки, ТО каждый рынок ДОЛЖЕН показываться с флагом, названием и валютой
3. КОГДА пользователь выбирает рынки через чекбоксы, ТО система ДОЛЖНА отслеживать выбранные рынки
4. КОГДА выбран хотя бы один рынок, ТО кнопка "Настроить цены" ДОЛЖНА стать активной
5. КОГДА пользователь нажимает "Назад", ТО система ДОЛЖНА вернуться к предыдущему шагу с сохранением выбранных данных

### Требование 5: Настройка правил ценообразования

**Пользовательская история:** Как пользователь, я хочу настроить правила ценообразования для каждого выбранного рынка, чтобы цены соответствовали местным условиям.

#### Критерии приемки

1. КОГДА пользователь переходит к настройке цен, ТО система ДОЛЖНА создать карточку настроек для каждого выбранного рынка
2. КОГДА пользователь выбирает тип правила ценообразования, ТО система ДОЛЖНА отобразить соответствующие поля ввода (коэффициент, фиксированная сумма, процент наценки)
3. КОГДА пользователь нажимает "Рассчитать цены", ТО система ДОЛЖНА выполнить предварительный расчет через API `/api/v1/markets/pricing/preview` и показать результат в таблице
4. КОГДА пользователь вводит название шаблона, ТО система ДОЛЖНА сохранить настройки как шаблон при запуске переноса
5. КОГДА пользователь нажимает "Запустить перенос", ТО система ДОЛЖНА показать подтверждающий диалог с количеством офферов и рынков

### Требование 6: Мониторинг процесса переноса

**Пользовательская история:** Как пользователь, я хочу видеть прогресс переноса офферов в реальном времени, чтобы контролировать процесс и видеть результаты.

#### Критерии приемки

1. КОГДА перенос запущен, ТО система ДОЛЖНА создать WebSocket соединение для мониторинга сессии
2. КОГДА система получает обновления через WebSocket, ТО она ДОЛЖНА обновлять прогресс-бар, счетчики успешных/неудачных офферов
3. КОГДА обновляется статус отдельного оффера, ТО система ДОЛЖНА обновить его карточку с новым статусом, новым ID или сообщением об ошибке
4. КОГДА сессия имеет статус "running", ТО система ДОЛЖНА показывать кнопки "Приостановить" и "Отменить"
5. КОГДА сессия имеет статус "paused", ТО система ДОЛЖНА показывать кнопки "Возобновить" и "Отменить"
6. КОГДА сессия завершается, ТО система ДОЛЖНА показать итоговую статистику и уведомление о завершении

### Требование 7: Управление шаблонами

**Пользовательская история:** Как пользователь, я хочу сохранять и использовать шаблоны настроек переноса, чтобы не настраивать одинаковые параметры повторно.

#### Критерии приемки

1. КОГДА пользователь заходит в раздел шаблонов, ТО система ДОЛЖНА загрузить список сохраненных шаблонов через API `/api/v1/offer-transfer/templates/`
2. КОГДА пользователь создает новый шаблон, ТО система ДОЛЖНА сохранить его через API с названием, описанием, рынками и правилами ценообразования
3. КОГДА пользователь выбирает существующий шаблон, ТО система ДОЛЖНА применить его настройки к текущему процессу переноса
4. КОГДА пользователь редактирует шаблон, ТО система ДОЛЖНА обновить его через API
5. КОГДА пользователь удаляет шаблон, ТО система ДОЛЖНА показать подтверждающий диалог и удалить шаблон через API

### Требование 8: Система мониторинга и метрик

**Пользовательская история:** Как администратор, я хочу видеть общие метрики системы и состояние активных сессий, чтобы контролировать работу системы.

#### Критерии приемки

1. КОГДА пользователь заходит в раздел мониторинга, ТО система ДОЛЖНА загрузить метрики через API `/api/v1/monitoring/metrics`
2. КОГДА система отображает метрики, ТО она ДОЛЖНА показать активные сессии, обработанные офферы, успешность, среднее время обработки
3. КОГДА система показывает распределение по рынкам, ТО она ДОЛЖНА отобразить его в виде горизонтальных полос с процентами
4. КОГДА система обновляет метрики, ТО она ДОЛЖНА делать это автоматически каждые 30 секунд
5. КОГДА система показывает топ ошибок, ТО она ДОЛЖНА отобразить их с количеством и процентами

### Требование 9: Обработка ошибок и уведомления

**Пользовательская история:** Как пользователь, я хочу получать понятные уведомления об ошибках и успешных операциях, чтобы понимать состояние системы.

#### Критерии приемки

1. КОГДА происходит ошибка API, ТО система ДОЛЖНА показать уведомление с понятным описанием проблемы
2. КОГДА происходит ошибка авторизации (401), ТО система ДОЛЖНА перенаправить на страницу входа
3. КОГДА происходит ошибка сети, ТО система ДОЛЖНА показать уведомление о проблемах с подключением
4. КОГДА операция выполняется успешно, ТО система ДОЛЖНА показать уведомление об успехе
5. КОГДА уведомление показано, ТО оно ДОЛЖНО автоматически исчезнуть через 5 секунд или при нажатии кнопки закрытия

### Требование 10: Адаптивный дизайн и производительность

**Пользовательская история:** Как пользователь, я хочу использовать систему на разных устройствах с хорошей производительностью, чтобы работать удобно в любых условиях.

#### Критерии приемки

1. КОГДА пользователь открывает систему на мобильном устройстве, ТО интерфейс ДОЛЖЕН адаптироваться под размер экрана
2. КОГДА система загружает большие списки офферов, ТО она ДОЛЖНА использовать пагинацию или виртуализацию для производительности
3. КОГДА выполняются длительные операции, ТО система ДОЛЖНА показывать индикаторы загрузки
4. КОГДА пользователь взаимодействует с элементами, ТО система ДОЛЖНА реагировать мгновенно без задержек
5. КОГДА система кэширует данные, ТО она ДОЛЖНА обновлять их при необходимости без потери актуальности
